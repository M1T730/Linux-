# Stage 3 — Identity, Automation & Network Services

**Objective:**
Transform a protected observable infrastructure into a **centrally managed, automated, and self-sufficient network environment**.
This stage introduces unified authentication, infrastructure-as-code, and authoritative network services.
The goal is to ensure that:

- users and machines authenticate through a single identity provider
- infrastructure changes are reproducible and version-controlled
- DNS resolution is handled internally without external dependency
- IP address assignment is managed and tracked centrally

# Core Capabilities Introduced

## 1. Identity Management

A **centralized directory service** is introduced to unify authentication across the entire infrastructure.

Typical setup:

- **Active Directory Domain Services (AD DS)**
- single domain for all lab machines and users
- Group Policy Objects (GPOs) for enforcing configuration
- Organizational Units (OUs) for logical segmentation
- domain join for Linux and Windows machines

Example organizational structure:

```
lab.local
├── OU=Servers
│   ├── proxmox-node
│   └── dns-server
├── OU=Workstations
│   └── dev-machine
└── OU=Users
    ├── admin
    └── readonly
```

Benefits:

- single set of credentials across all services
- centralized password policy enforcement
- audit trail for authentication events
- foundation for SSO integration in later stages

---

## 2. Group Policy & Access Control

Active Directory enables **declarative configuration enforcement** across joined machines.

Typical policies:

| Policy | Scope |
|---|---|
| Password complexity | All users |
| Login banner | All machines |
| Disable USB storage | Servers OU |
| Enforce screen lock | Workstations OU |
| Restrict local admin | Domain machines |

This removes the need for per-machine manual hardening, replacing it with a single managed policy layer.

---

## 3. Infrastructure Automation

Manual configuration is replaced by **idempotent, version-controlled playbooks**.

Typical setup:

- **Ansible** as the automation engine
- **Ansible Vault** for secrets management
- a dedicated Git repository as the source of truth for all infrastructure state

Example playbook scope:

| Playbook | Purpose |
|---|---|
| `provision_vm.yml` | bootstrap a new VM with base packages |
| `configure_dns.yml` | deploy and update BIND9 zones |
| `harden_host.yml` | apply SSH, firewall, and sysctl settings |
| `deploy_service.yml` | install and configure a monitored service |

Ansible inventory mirrors the AD OU structure, grouping hosts by role. All playbooks are stored in Git, making every infrastructure change reviewable and reversible.

A key operational shift occurs here: **no configuration change is made manually**. Every change goes through a playbook, ensuring the repository always reflects the real state of the infrastructure.

## 4. Authoritative DNS

An internal DNS server replaces reliance on upstream resolvers for lab domains, giving the infrastructure **full control over name resolution**.

Typical setup:

- **BIND9** as the authoritative nameserver
- a dedicated internal zone (e.g. `lab.local`)
- forward zones for internal services
- reverse zones for PTR record resolution
- conditional forwarding for external domains

Example zone structure:

```
lab.local.
├── proxmox.lab.local       → 10.10.1.10
├── ad.lab.local            → 10.10.1.11
├── dns.lab.local           → 10.10.1.12
├── grafana.lab.local       → 10.10.1.20
└── jellyfin.lab.local      → 10.10.1.30
```

Benefits:

- services are reachable by name, not by IP
- internal traffic never leaves the network for resolution
- DNS records are managed alongside infrastructure code via Ansible
- reverse lookups support logging and monitoring readability

## 5. DHCP Server

A managed DHCP service replaces router-based address assignment, introducing **controlled and auditable IP allocation**.

Typical setup:

- **ISC DHCP Server** or **Kea DHCP**
- scopes aligned to VLAN structure defined in Stage 2
- static leases for all infrastructure hosts
- dynamic pool for temporary or guest devices

Example scope configuration:

| VLAN | Subnet | Static Lease Range | Dynamic Pool |
|---|---|---|---|
| VLAN10 – Lab Servers | 10.10.1.0/24 | .1 – .50 | .100 – .200 |
| VLAN20 – Management | 10.10.2.0/24 | .1 – .20 | — |
| VLAN30 – Clients | 10.10.3.0/24 | — | .50 – .200 |

DHCP and DNS are integrated: lease assignments automatically update DNS records, ensuring that every device has a resolvable hostname from the moment it joins the network.
